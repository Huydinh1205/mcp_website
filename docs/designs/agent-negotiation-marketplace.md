## Problem Statement

Build a multi-vendor marketplace (Temu-style: many sellers, many buyers, one
catalog) for the OpenAI WebMCP Challenge. The differentiator: both buyers and
sellers operate their own AI agents that browse, compare, negotiate price, and
close deals through structured tools the site exposes via WebMCP
(`document.modelContext.registerTool()`), not by clicking a normal UI. Every
state-changing action (accepting a deal, checkout) requires explicit human
confirmation before it executes.

The challenge exists because most WebMCP demo ideas (booking assistants,
shopping helpers) just make one agent click faster than a human. Agent-to-agent
price negotiation is different: two independent agents that otherwise have no
channel to talk can only coordinate through a shared structured interface.

## What Makes This Cool

- **Two independent LLM agents, in two browser windows, converging on a price in
  real time.** Buyer's agent and seller's agent each run their own client-side
  agent loop against their own page's WebMCP tools. Offer -> counter -> counter
  -> accept, price ladder animating in both windows.
- **The marketplace backend is the message bus, not a peer connection.** Neither
  agent talks to the other. Both read and write negotiation rounds on the
  marketplace; each page polls for changes (1-2s). WebMCP is the coordination
  protocol; the DB is the single source of truth.
- **Each human confirms once.** The agents do all the haggling; each human sees
  a converged deal and taps confirm. The order finalizes only when both have.

## Landscape Notes

- **WebMCP API:** `document.modelContext.registerTool(def)` /
  `.unregisterTool(name)` / `.request`. `navigator.modelContext` is deprecated as
  of Chromium 150. Chrome 146+ only.
- **The agent that consumes the tools is a tool-agnostic harness** (D-A1): it
  discovers tools by introspecting the `document.modelContext` registry, not by
  importing the page's functions. The same harness would run on any WebMCP site.
  This is the honest demonstration and the reference pattern
  (`jonasneves/webmcp`, `WebMCP-org/examples`). Evaluate reusing one of those
  runtimes on Day 1 with a 30-min timebox; otherwise the harness is ~120-150
  lines (D-A5) and fully under our control.

### Component decisions

- **D-A1 — Tool boundary:** the harness imports nothing from the marketplace
  page. It reads the WebMCP registry, builds tool schemas, and invokes tools
  through the WebMCP call path.
- **D-A2 — Turn arbitration:** `Negotiation` row carries `Last_Actor`
  (`buyer|seller`) and `Current_Round` (int). An agent acts ONLY when
  `Last_Actor != itself` AND `Status == 'countered'`. Every mutating call passes
  the round it read; the DB write is `... WHERE id = ? AND Current_Round = ?` —
  0 rows affected means a stale turn, drop it. On success: `Current_Round++`,
  `Last_Actor = me`. Terminal statuses (`confirmed`, `rejected`) freeze the row.
- **D-A3 — Transport:** polling, not SSE. Both pages call
  `GET /api/negotiations?since=<cursor>` every 1-2s. Removes the Vercel
  serverless long-connection footgun. (Supabase Realtime is an acceptable
  swap-in if the teammate is already on Supabase.)
- **D-A4 — Confirmation state machine:**
  ```
  buyer agent accept_offer()   -> Status = buyer_accepted, confirm_token
  buyer human confirm POST     -> Order.Buyer_Confirmed_At = now
  seller agent respond(accept) -> Status = seller_accepted, confirm_token
  seller human confirm POST    -> Order.Seller_Confirmed_At = now
  both timestamps set          -> Status = confirmed, order is live
  ```
  No agent path finalizes an order. `accept_offer` / `respond_to_offer(accept)`
  only issue a token.
- **D-A5 — Agent loop:** hand-rolled chat-completions tool-call loop (~120-150
  lines). Build tool schemas from the WebMCP registry, call
  `chat.completions` with `tools` + `temperature: 0`, execute returned
  `tool_calls` via the WebMCP path, append results, loop until no tool call or
  round cap. Emit one event per step to the transcript UI. Not the Agents SDK —
  it fights the custom streaming, round cap, and determinism needs.
- **D-C1 — Single source of truth:** `lib/offers.ts` exports
  `applyTurn({ negotiationId, actor, action, price, roundSeen })` returning
  `Result<Negotiation, TurnError>`. It does the optimistic round check, floor/cap
  enforcement, state transition, `Last_Actor` flip, round append, and returns
  the new state or a typed rejection. Buyer tools, seller tools, and any
  server-side path are thin wrappers. This is the one function the whole demo
  rests on — unit-tested hard (D-T1).

### Data model — required changes to `database_architecture.png` (D-C2)

The teammate's ERD is the base. Normalized `Negotiation` + `Negotiation_Round`
is kept (better than a `history jsonb` blob). Add, before writing seed data:

| Table | Add | Why |
|-------|-----|-----|
| `Negotiation` | `Last_Actor ENUM('buyer','seller')`, `Current_Round INT` | D-A2 turn token + optimistic guard |
| `Negotiation` | pin `Status ENUM('open','countered','buyer_accepted','seller_accepted','confirmed','rejected')` | D-A2/D-A4 state machine |
| `Order` | `Buyer_Confirmed_At TIMESTAMP NULL`, `Seller_Confirmed_At TIMESTAMP NULL` | D-A4 both-confirm finalization |
| `Negotiation_Round` | ensure an author/actor column (or derive from `Last_Actor` at write time) | so a round knows who proposed it |

`Negotiation.Order_ID` stays nullable until confirm. `Negotiation.National_ID` =
the buyer; the seller is reached via `Product.National_ID`.

Agent strategy lives in `Buyer_AI_Config` (`Max_Budget`, `Target_Price`,
`Min_Seller_Rating`, `Style`) and `Seller_AI_Config` (`Auto_Accept_Price`,
`Max_Discount_Step`, per `Product_ID`). The harness turns these rows into the
persona system prompt.

1. **Polling too chatty / laggy** -> widen interval or move to Supabase Realtime.
2. **Seller browser agent loop not converging reliably by midday Sept 2** ->

3. **Still shaky Sept 3 morning** -> scripted seller responses for the video
   only; everything else live.
4. **Demo determinism:** seeded product + `temperature: 0` + round cap 3-4 so the
   pair always converges or ends in a clean "no deal."

## Failure modes (per new codepath)

| Codepath | Realistic failure | Test? | Error handling? | User sees? |
|----------|-------------------|-------|-----------------|------------|
| `applyTurn()` stale turn | two loops write same round | YES (D-T1) | typed rejection, drop turn | nothing (silent, correct) |
| `applyTurn()` no-deal at round cap | agents never converge | YES (D-T1) | `Status = rejected` | "no deal" in both transcripts |
| harness | LLM returns malformed/unknown tool_call | deferred (TODO) | **must** catch + skip or abort loop | risk: silent hang — **add a guard even though the test is deferred** |
| `/api/agent/turn` | OpenAI 429 / timeout mid-negotiation | deferred (TODO) | retry once, then surface | transcript shows "agent stalled" |
| `/api/orders/confirm` | double-click / reused token | deferred (TODO) | idempotent on token | one order, no error |
| polling | cursor skips an update | deferred | full-state refetch every N polls | transient, self-heals |

**Critical gap flagged:** harness handling of a malformed/unknown `tool_call` has
no test AND, if unhandled, is a silent hang on stage. Even though D-T1 defers the
harness *test*, the plan must include the *guard* (catch unknown tool name ->
emit an error event -> abort the loop cleanly) as part of Day-1 harness work.
